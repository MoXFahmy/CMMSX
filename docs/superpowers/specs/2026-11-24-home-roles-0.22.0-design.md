# Home pages and roles (0.22.0)

Roadmap item from the DimoMaint comparison: home cards per role, counters from saved views, shortcut tiles and menu
restrictions. Choice A, picked in the conversation: **the administrator arranges each role's home; people add only
their own counter tiles.**

## Intent

Today everyone lands on the same dashboard: asset charts and work counts that suit a maintenance manager but not a
technician, a storekeeper or someone who only reports problems. DimoMaint lets each role open on what it needs and
lets people pin the numbers they watch. CMX should do the same, keeping it simple and consistent: a manager decides
what each role sees first, everyone with that role sees the same layout, and each person adds the counters they care
about from the saved views they already have.

Success looks like: a technician opens CMX and sees their own work, late work and a "report a problem" button; a
storekeeper sees low stock and approvals; a manager keeps today's dashboard; anyone can pin "My late PMs at Site B" and
see its number on the home page without opening the list.

## Goals

1. **Role home pages.** An administrator (users.manage) gives each role an ordered list of home cards, chosen from a
   fixed catalogue: the pieces of today's dashboard plus new cards (my work, unassigned work, late work, assets down,
   low stock, waiting for my approval, quick request, location tree, shortcut tiles).
2. **Personal counters.** Anyone can pin their saved views to the home page as counter tiles (up to 24). Each tile
   shows how many records match right now and opens the list with that view.
3. **Shortcut tiles.** A card of coloured tiles, each with a label and a CMX link, set by the administrator per role.
4. **Menu tidying per role.** An administrator can hide menu items for a role. Permissions still decide access; the
   screen says so.
5. **Default columns per role.** An administrator can make a list's current columns the default for a role. They apply
   until a person picks their own.
6. **Duplicate role.** One button copies a role with its permissions, home, menu and default columns.
7. A role with no home set up keeps today's dashboard, so nothing changes for anyone until an administrator acts.

## Non-goals

- People arranging their own cards (choice B). People only add, order and remove their own counters.
- Drag-and-drop editing on the home page itself. The role editor uses move up / move down.
- Configurable charts, custom queries or card sizes. Cards are a fixed catalogue with fixed sizes.
- External links in shortcut tiles. Tiles open CMX pages only.
- Hiding Home or Settings from the menu.
- The phone (technician view). It keeps its own start screen.
- Restricting data by role beyond permissions. Hiding a menu item never blocks access.
- A "preview as this role" mode.

## Anti-goals

- **A menu restriction that people mistake for security.** Hiding is tidying; every screen that hides something says
  that permissions decide access.
- **Cards that show data a person can't otherwise see.** Each card asks the same endpoints the lists use, so site
  access and permissions apply as they do today. A card the person can't use is left out, never shown empty or broken.
- **Counters that disagree with their list.** A tile's number must equal the total the list shows for the same view.
- **Changing anyone's screen on upgrade.** No role gets a home by default.

## Approaches considered

- **A. Administrator per role, personal counters** (picked). One layout per role, set in the role editor; people add
  counters from their saved views. Consistent, little UI, and matches how DimoMaint is used by the partner.
- **B. Each person arranges their own home** from a starting layout the administrator sets. More freedom, but every
  person's screen differs, support gets harder, and it needs a full editor on the home page.
- **C. One home for the whole organization**, cards hidden by permission. Simplest, but can't put "report a problem"
  first for requesters and charts first for managers.

For counter numbers inside A: **counted in the browser through each list's own endpoint** (picked), using the same
function the list page uses to turn its address into a query, with page size 1 and reading `total`. The alternative, a
server endpoint that counts many views at once, would need the server to parse address queries (tabs, "view=mine",
etc.), which the list pages map in the browser today; the two copies would drift and break the "same as the list" rule.

## Design

### 1. Card catalogue

Each card has a fixed type key, a width (full or half; half cards pair up two per row on wide screens and stack on
phones) and the permissions it needs. A card whose permissions the person lacks is left out of their home.

| Key | Card | Needs | Width | Data / link |
|---|---|---|---|---|
| `work-summary` | Work counters (today's six) | dashboard.view + workorders.view | full | /api/dashboard |
| `work-by-site` | Work by site table | dashboard.view + workorders.view | full | /api/dashboard |
| `urgent-work` | Urgent work | dashboard.view + workorders.view | half | /api/dashboard |
| `asset-summary` | Asset counters | dashboard.view | full | /api/dashboard |
| `assets-by-status` | Assets by status donut | dashboard.view | half | /api/dashboard |
| `assets-by-category` | Assets by category bars | dashboard.view | half | /api/dashboard |
| `assets-by-site` | Assets by site | dashboard.view | half | /api/dashboard |
| `warranty-soon` | Warranties ending soon | dashboard.view | half | /api/dashboard |
| `recent-assets` | Recently added assets | dashboard.view | half | /api/dashboard |
| `my-work` | My work | workorders.view | half | /work-orders?view=mine |
| `unassigned-work` | Unassigned work | workorders.view | half | /work-orders?view=unassigned |
| `late-work` | Late work | workorders.view | half | /work-orders?view=overdue |
| `assets-down` | Assets down now | assets.view | half | /assets?downNow=true |
| `low-stock` | Parts below reorder level | inventory.view | half | /inventory?low=true |
| `my-approvals` | Waiting for my approval | purchasing.approve or purchasing.approveRequests | half | /approvals/mine, link /approvals |
| `quick-request` | Report a problem | requests.create | half | opens the existing request form |
| `location-tree` | Location tree | locations.view | full | /locations hierarchy |
| `shortcuts` | Shortcut tiles | none (each page checks its own) | full | the tiles' links |

- **Dashboard pieces.** Today's `DashboardPage` is split into these section components, each unchanged in what it
  shows and links to. Cards that need /api/dashboard share one fetch.
- **Today's dashboard stays exactly as it looks** for people without a role home: the same nine sections in today's
  arrangement (urgent work full width, status and category split 5:7, assets by site, warranties and recent assets three
  to a row) and today's empty-organization screen (no sites and no assets). It is built from the same section
  components but keeps its own fixed arrangement; it does not go through the card grid. (My call: the anti-goal says
  nobody's screen changes on upgrade.)
- **Role homes use the card grid**: full cards take a row; half cards pair up two per row on wide screens, in order;
  a half card followed by a full card sits alone at half width. "Start from today's dashboard" adds the same nine
  cards in the same order; their arrangement then follows the grid, so it looks close to, not identical with, the
  standard dashboard. The editor says so in one line.
- **List cards** (my work, unassigned, late, assets down, low stock) show the list's total in the card header with a
  "View all" link, and the first 8 rows (number or code, title or name, one short secondary line). They fetch the list
  endpoint with the same query their link opens, through the shared address-to-query functions (section 3), sorted so
  the most pressing come first (my work and late work: earliest due first; unassigned: highest priority, then oldest;
  assets down: longest down first; low stock: furthest below reorder first, or the list's default if it has no such
  sort). The card total must equal the list total.
- **Unassigned work** is new: active work orders with no person assigned (a team may be set; the card is for whoever
  hands out work). The server's work order filter gains `Unassigned` (`!w.Assignees.Any()`), and the work order list's
  view choice gains "Unassigned" (`view=unassigned`), so the card's link opens a real list view.
- **My approvals** shows the count of requests and orders waiting for my signature and the first 8 of them, from
  `/approvals/mine`; "View all" opens My approvals.
- **Quick request** shows one line of text and a "Report a problem" button that opens the existing request form
  (`RequestFormModal`).
- **Location tree** reuses the locations page tree (extracted into a shared component: build, search, expand). Picking
  a site or location shows its name and buttons, each shown only with its permission: Report a problem here
  (requests.create, form opened with the location set), New work order here (workorders.create), New asset here
  (assets.create), Open (the locations page with it selected). Where a form does not yet accept a location to start
  with, add that.
- **My work** is left out for people with no linked employee record, like a card they can't use: work is assigned to
  employees, so the list would always be empty for them. (My call.)
- **Shortcut tiles.** One `shortcuts` card holds up to 12 tiles. A tile has a label and an optional Arabic label (up
  to 40 characters each; the label is required), following the `Name` / `NameAr` pattern of 0.21.0's lists and units:
  people using CMX in Arabic see the Arabic label when there is one. It also has a colour from a fixed set (blue, teal,
  green, orange, red, grape, indigo, gray; theme-aware) and a link that is a CMX address starting with `/` (up to 300
  characters, not `//`, no scheme, no backslash). Tiles open with the app's router. (Arabic label: my call.)

### 2. Role home, menu and default columns

**Data model**

- `Role.HomeLayout`: the ordered cards, stored as JSON on the role row (nullable). Each card is `{ type, tiles? }`,
  where tiles only belong to `shortcuts`. Null or an empty list means "not set up": that role contributes no cards.
  Up to 20 cards per role.
- `Role.HiddenModules`: menu item keys hidden for the role (a string list, default empty). Keys are fixed in Core
  (`MenuModules.All`), each with the permission(s) the menu already uses to show it (any one of them is enough):
  locations (locations.view), assets (assets.view), work-requests (requests.create), work-orders, work-groups,
  planning, availability, timesheet (all workorders.view), pm (pm.view), contracts (contracts.view), inventory
  (inventory.view), purchasing (purchasing.view, purchasing.request or purchasing.approveRequests), approvals
  (purchasing.approve or purchasing.approveRequests), reports, budgets (both reports.view), people (people.view). The
  web menu reads its keys and permissions from the same list, so the two can't drift. Home and Settings have no key and
  can't be hidden.
- `RoleListSetting` (new table, mirrors `UserListSetting`): tenant, role, list key, hidden-column tokens in the same
  `x` / `+x` form the list toolkit already uses. One row per role and list.

**Endpoints** (all under `/roles`, users.manage, as today)

- `RoleInput` gains `List<HomeCardInput>? Home = null` and `List<string>? HiddenModules = null`, old-client pattern:
  null leaves the value unchanged. Create and update both accept them; the role window saves everything in one
  request. Validation: known card types, at most 20 cards, tiles only on `shortcuts`, at most 12 tiles, label required
  and up to 40 characters, colour in the set, link rules above, module keys known. The Administrator role may have a
  home and hidden modules like any role.
- `GET /roles` adds `home`, `hiddenModules` and `defaultColumns` (the list keys that have a role default).
- `PUT /roles/{id}/columns/{list}` sets a role's default columns for a list (see Default columns below);
  `DELETE /roles/{id}/columns/{list}` clears it. Unknown list keys answer 400, as views do.
- `POST /roles/{id}/duplicate` creates "‹name› (copy)" (numbered if taken) with the description, permissions, home,
  hidden modules and default columns, and no people. Duplicating Administrator gives an ordinary role with every
  permission.
- Deleting a role removes its default columns.

**For the signed-in person** (`GET /auth/me` gains `home`)

- `home.cards`: the cards of all the person's roles, roles taken in name order (case-insensitive), without repeats: a
  card type already taken is skipped, except `shortcuts`, whose tiles are kept unless a tile with the same link was
  already shown (a shortcuts card left with no tiles is dropped). Empty when no role has a home.
- `home.hiddenModules`: a menu item is hidden when every one of the person's roles that **gives its permission** hides
  it. A role that doesn't give the item's permission has no say: it couldn't show the item anyway, so an administrator
  never has to hide items on roles that can't see them. A person with no roles, or whose roles give the permission and
  don't hide it, sees the item as today. (My call.)
- People with several roles: the role window says "People with several roles see the cards of all their roles, in
  role-name order, without repeats" and "A menu item is hidden for a person when all of their roles that can open it
  hide it."

**Default columns**

- `GET /auth/me/list-settings` fills in, for each list the person has no own setting for, the default of the first of
  their roles (by name) that has one, marked as coming from the role. The list's columns then show those.
- **What counts as picking their own:** anything that saves a person's column setting today, that is, changing columns
  in the column menu or applying a saved view (including the person's default view, which applies itself when the
  list opens with an empty address). A view carries its own columns, and a view is the person's own choice. This is
  unchanged behaviour. (My call.)
- **Reset columns** is new on every toolkit list's column menu: it removes the person's own setting
  (`DELETE /auth/me/list-settings/{list}`), so the role's default comes back, or with no role default the list's
  built-in defaults, as today. (My call: needed for "until a person picks their own" to be reversible.)
- In each list's column menu, people with users.manage get "Use these columns for a role…", which picks a role and
  saves the current column choice as that role's default for this list. When some people with that role already have
  their own columns on that list, the same window shows how many and offers a checkbox, off by default: "Also reset
  the columns of the N people with this role who changed theirs." Ticking it removes those people's own settings for
  that list only. Without that, a new role default would reach almost nobody who already uses the list. (My call.)
  The endpoint is `PUT /roles/{id}/columns/{list}` with `{ hiddenColumns, resetMembers }`; `GET /roles/{id}/columns/{list}/changed`
  (or a count in the PUT's dry run, builder's choice) gives N.
- The role window's Columns tab lists the lists that have a default for this role, each with "Clear".

**Role window** (Settings › Roles; same window, now with tabs)

- **Permissions**: as today.
- **Home page**: the role's cards in order, each with its name, a one-line description, move up, move down and remove.
  "Add card" picks from the catalogue, grouped (Dashboard pieces / Work / Assets and stock / Tools); a type already in
  the list can't be added twice (except that there is only one shortcuts card, holding all tiles). "Start from today's
  dashboard" fills in the classic layout. A card the role's permissions don't cover is marked: "People with only this
  role won't see this card: it needs ‹permission name›." The shortcuts card opens a small tile editor (label, colour,
  link; the link field offers the menu pages and "New work order", "New request", "New asset", and accepts a typed CMX
  address). With no cards: "No home page: people with this role see the standard dashboard."
- **Menu**: a checkbox per menu item, "Show in menu", with the note: "Hiding a menu item only tidies the menu. People
  can still open the page from links if their permissions allow it. To stop access, change the role's permissions."
- **Columns**: the lists with a role default and a Clear button each, plus where to set one.
- The roles table gets a "Duplicate" action and a small "Home" badge on roles with a home set up.

### 3. Personal counters

- `SavedView` gains `PinnedToHome` (bool) and `HomeOrder` (int). A person may pin up to 24 views across all lists;
  the 25th answers "You can pin up to 24 views to your home page. Unpin one first."
- `PUT /views/{id}/pin` with `{ pinned }`; `PUT /views/home-order` with the person's pinned view ids in order;
  `GET /views/home` returns the person's pinned views `{ id, list, name, query }` in order. All personal, as views are
  today: another person's id answers 404. Deleting a view unpins it with it.
- The saved-views menu in the list toolkit gets "Show on home page" / "Remove from home page" per view.
- **Address-to-query functions.** For each of the six toolkit lists, the code that turns the list page's address into
  its API query moves out of the page into one shared module, one function per list
  (`(params: URLSearchParams, can) => query`; the permission check is there because some lists pick their default tab
  by permission, as work requests do). The page uses it, and so do the counter tiles and list cards. That is how a
  tile's number equals the list's total.
- A pinned view whose query is empty opens the list's plain view, not the person's default view (the tile's link must
  stop the default view from applying itself), so the list shows what the tile counted.
- **Tiles** sit in a "My counters" row at the top of the home page, above the role's cards, or above today's dashboard
  for people without a role home. Each tile shows the view's name, the count (large), the list's name, and opens the
  list with the view's query. Its menu: Move earlier, Move later, Remove from home. Counts are fetched with page size 1
  and refreshed every minute while the page is open. A tile for a list the person can no longer see shows "No access"
  and fetches nothing; a failed count shows "—" with the error on hover.
- People with no pinned views see one quiet line under the greeting: "Pin a saved view to see its count here."

### 4. Home page and menu

- The index route renders the **home page**: greeting, My counters, then either the person's role cards (if
  `home.cards` has any they can use) or today's dashboard.
- A person without dashboard.view and without a role home today sees an endless spinner. They now see the greeting,
  their counters, and "Your home page has nothing to show yet. Ask your administrator to set one up for your role."
- The menu's first item reads **Home** for people with a role home and **Dashboard** otherwise, and shows when the
  person has a role home or dashboard.view.
- Menu items whose key is in `home.hiddenModules` are left out. Direct links and in-page links still work under
  permissions.

### Permissions

No new permissions. users.manage edits roles (as today, including home, menu, columns and duplicate). Saved views and
pins are personal and need only a sign-in. Every card's data comes from endpoints that already check permissions and
sites.

### Arabic

Every new label, card name, description, note and message in English and Arabic, with Arabic plural forms where a
count is shown.

## What's left to the builder

- The JSON storage mechanics for `HomeLayout` (owned JSON column or a converter) and the migration's name.
- Exact component split of today's dashboard and where the shared tree and address-to-query modules live.
- Card visuals within the existing Mantine style, including empty states for each list card ("Nothing late. Good.").
- How the tile editor and card list look inside the role window.
- The sort used by each list card where the list has no matching sort, within the "most pressing first" intent.
- Whether the counters' one-minute refresh pauses while the tab is hidden.
- A short user guide, `docs/HOME_PAGES_AND_ROLES.md`, in the style of the earlier guides.

## Tests that matter most

- Role home round trip and validation: unknown card, 21 cards, tiles on a non-shortcuts card, 13 tiles, an
  `https://` or `//` link, an unknown colour, an unknown module key: each refused with a field message.
- `/auth/me` home merge: two roles in name order, a repeated card type kept once, shortcut tiles merged without
  repeated links, a role with no home contributing nothing, no roles with homes giving empty cards.
- Hidden modules: hidden when all of a person's roles that give the item's permission hide it; a role without the
  permission doesn't keep it showing; no roles hides nothing.
- Default columns: the person's own setting beats the role's; the first role by name wins among roles; Reset columns
  brings the role default back; clearing the role default brings the built-in defaults back; "also reset" removes
  only that role's members' settings for that list, and only when ticked.
- Duplicate role copies permissions, home, hidden modules and default columns, not people, and names "(copy)",
  "(copy 2)".
- Pins: the 25th refused, order kept, another person's view 404, deleting a view removes its pin.
- The `Unassigned` filter: a work order with only a team counts, one with any person doesn't.
- Address-to-query functions: for each list, several addresses (tabs, views, filters, empty) give the same query the
  page sends; a counter and the list agree for the same view against the API.
- Home page: role cards shown in order and filtered by permission; no role home gives today's dashboard in today's
  arrangement; no dashboard.view and no home gives the message, not a spinner; hidden menu items left out;
  Home/Dashboard label; a tile's Arabic label shown in Arabic.
- Role window: the "won't see this card" marking for missing permissions; "Start from today's dashboard" gives the
  nine pieces in order.
