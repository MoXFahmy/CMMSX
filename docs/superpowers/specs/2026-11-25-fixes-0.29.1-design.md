# CMX 0.29.1 — privacy and data-safety fixes (design)

Approved in conversation on 25 November 2026. The item list comes from part 6 of `CMX left-overs up to 0.28.0.md` in the CMX Drive
folder. Each item there is tagged (for example `0.10.0-1`) and described in its release's section of that file. This design keeps
those tags so every fix traces back to its item.

## Intent

0.29.0 made CMX's platform secure and its backups safe. 0.29.1 does the same for CMX's own behaviour before 0.30.0 adds new
client security controls. It fixes the 42 left-overs that can't wait for their area's roadmap release:

- people seeing or reaching things they shouldn't;
- a safety gate that can be skipped;
- data lost or kept without telling anyone;
- wrong totals;
- double records when two people act at once;
- server errors on ordinary input.

It also adds a guard test against a class of leak that has happened three times, and closes a few gaps in 0.29.0's operations.

## Goals

- Every one of the 42 items behaves as described below, each proven by a test that fails on 0.29.0 and passes after the fix.
- A source-scan guard test that fails the build when a query lifts its own organization or site filter.
- Refused sign-ins are visible to the sign-in alarm; CloudFront errors raise an alarm.
- The Azure setup uses GitHub's current sign-in subject, as the AWS one has since commit 195cc61.

## Non-goals

- New features, screens or settings. The only additions are messages and one confirmation dialog.
- The other 164 left-overs, which ride with their roadmap release, and the Arabic polish, which is 0.29.2.
- Single sign-on (parked).
- Redesigning any module the items touch.

## Anti-goals (a failure even if the fix "works")

- A fix that changes what an organization sees or can do beyond the item it fixes.
- Blocking a legitimate person's normal action without a clear message saying why and what to do instead.
- Any new leak across organizations, sites or permissions, including through e-mail, push, AI text, exports or the phone bundle.
- An IP address or e-mail address in any log line.

## Constraints (from the project and 0.29.0)

- Tests first for every item: write the test, see it fail on the current code, then fix. If the test passes before any fix, the
  item is already closed. Keep the test, record the item as "already fixed", and change no code for it.
- Server tests run against SQL Server through the existing fixture (`ApiFixture`). Web tests use Vitest. Phone changes need the
  phone shell's existing checks.
- Every new user-facing text has English and Arabic (`web/src/locales/en.json`, `ar.json`, and the server's own resources).
- No IP or e-mail address in logs (the 0.29.0 rule).
- A database migration only where a fix truly needs one (for example a unique index to stop double order lines). It must be safe
  on live data: check for existing duplicates and say in the migration how they are handled. No data is deleted.
- Infrastructure changes go through the pipeline (`deploy-aws.yml`), never by hand, and keep the 0.29.0 boundary and guard rules.
  No change may need `setup.sh` to be re-run unless it's unavoidable, and the design says so if it is.
- Release with `scripts/release.sh 0.29.1`. The user pushes from GitHub Desktop and the pipeline deploys.

## Approaches

1. **One release, built in about eight tasks grouped by area, each reviewed, then a whole-branch review** (chosen). Same process
   as 0.29.0. Grouping by area keeps each task's code in one place and lets a reviewer judge it on its own.
2. Two smaller releases: privacy and safety first, the rest after. Rejected: the user chose to put all 42 in 0.29.1. The items are
   small and independent, so one release costs less in deploys.
3. Fixing each item with its area's roadmap release. Rejected in the placement decision: some would wait months.

## Decisions made with the user (25 November 2026)

## Intended behaviour, item by item

### A. Seeing or reaching what you shouldn't (10)

- **0.10.0-1:** the public answer page's GET no longer returns the requester's name; it returns only what the page shows.
- **0.10.0-11:** decision 7.
- **0.12.0-1:** template documents are listed and downloaded only by people with *View PM*. Template pickers show nothing to
  people without it.
- **0.12.0-13:** PM recipients are checked against site access when the PM is saved, using the same rule as sending. A
  recipient who can't see the PM's site is refused with a message naming them.
- **0.15.0-3:** decision 2. The diagnosis must record the work orders it was given, so the check can run when it is viewed.
  Diagnoses saved before 0.29.1 have no such record. They are shown only to people whose access covers the whole organization;
  everyone else sees the "used work you can't see" message with *Run again* (controller's call after the builder check: when
  in doubt, hide).
- **0.16.0-1:** "Waiting for your signature" e-mails go only to approvers who hold *Approve purchases* now and can see the
  order's site.
- **0.26.1-2:** anonymising a person also removes their address from the Reply-To of e-mails still queued. E-mails they
  trigger afterwards carry none.
- **0.26.1-3:** the contract hidden-asset check at `ContractEndpoints.cs:319-321` is made to work: the visibility test must not
  share a query with `AllSites()`. A site-limited person can no longer narrow an organization-wide contract's site while it
  covers assets they can't see (refused, with a message).
- **0.9.1-4:** removing a person's last "(deleted place)" asks for confirmation and says what access they will have afterwards
  (the stored site).
- **0.11.0-4:** the phone hides "Issue to a job" and the counts list from roles without the stock permission, and the server
  refuses those actions for them too.

### B. Safety gate (1)

- **0.13.0-6:** decision 1.

### C. Lost or silently kept (11)

- **0.8.0-4:** on a completed work order, ticking "asset down" doesn't start a stop. The form explains how to report a stop
  instead.
- **0.8.0-6:** clearing "Runs hours a day" clears the value.
- **0.12.0-3:** making a group is one transaction. A failure part-way leaves nothing behind.
- **0.12.0-6:** the import never clears the next due date of a meter PM that has calendar triggers. Reactivating a PM by import
  works out its calendar dates as the screen does.
- **0.13.0-2:** a phone photo for a step that was removed meanwhile is kept as a work-order attachment, with a note naming the
  step, instead of being rejected.
- **0.16.0-11:** "Short for work" no longer drops lines silently. The result lists any lines it couldn't use and why.
- **0.17.0-1:** decision 5.
- **0.17.0-2:** decision 6.
- **0.18.0-2:** saving a supplier row without "preferred" leaves the part's preferred supplier alone. Only an explicit un-star
  of that row clears it.
- **0.21.0-6:** each save that happens in two steps becomes one transaction. The builder lists the saves it found.
- **0.21.0-8:** importing an asset onto a PM that follows an asset group becomes a row error saying to add the asset to the
  group, instead of a silent drop.

### D. Wrong numbers (4)

- **0.9.1-1:** "Completed (30 days)" counts by the organization's local dates, the same as the list its link opens.
- **0.14.0-7:** asset work history counts each stop once, even when two work orders share it.
- **0.18.0-1:** decision 3.
- **0.20.0-3:** decision 4.

### E. Two people at once (5)

- **0.11.0-1:** decision 8.
- **0.11.0-3:** two simultaneous partial receipts on one order line can't receive more than the line. The second gets "changed by
  someone else, refresh".
- **0.16.0-4:** when an order line is linked to a purchase-request line, the order API checks that the link is valid: same
  organization, approved, and not already on a live order line.
- **0.16.0-5:** two buyers ordering the same request line at once end up with one live order line. The second gets a message.
- **0.24.0-2:** a quantity issue racing a switch to serial numbers can't leave stock and units out of step.

### F. Server errors on ordinary input (7)

Each of these now answers with a clear message (400 or 409) instead of a server error.

- **0.10.0-10:** the request form clears extra recipients the new site can't use. Clearing a window date sends an empty value
  correctly. A missing window item is a validation message.
- **0.13.0-3:** undefined answer values are refused. Number and meter values beyond what the database holds are refused with a
  range message. The phone shows that message instead of setting the change aside after retries.
- **0.18.0-13:** two people adding the same supplier at once: the second gets "already exists".
- **0.20.0-1:** the server checks that a chosen cost centre exists and is active (requests, PMs, assets, locations).
- **0.20.0-9:** two first saves of a budget at once: the second gets "changed by someone else".
- **0.21.0-11:** malformed payloads to the lists endpoint get a 400 with a message.
- **0.24.0-3:** duplicate store ids in a switch-to-serial request get a 400.

### G. One-click step, push notifications, tests (4)

- **0.16.0-3:** "Restart approval" asks for confirmation. The dialog says the round's signatures will be dropped and the first
  level e-mailed again.
- **0.11.0-9:** Firebase INVALID_ARGUMENT (400) and SENDER_ID_MISMATCH (403) answers mark the token dead, with no retries. Sent
  and failed push messages older than 30 days are cleaned up (builder's call on the exact age, stated in the plan).
- **0.11.0-11:**
  - The "Request approved" push opens a page that exists.
  - The guide's wording matches what the tap does.
  - Push registration for phone users without an employee link needs push code in the full web app, so it moves to 0.39.0
    (iOS and phone). Planning ruling P5.
- **0.7.0-14:** the tests use dates relative to today instead of a fixed 2026-12-01.

### H. Extras

- **Guard test:** a server test that scans the source for `AllSites()` / `IgnoreQueryFilters()` used inside a query that also
  depends on the organization or site filter, and fails the build when it finds one. It must:
  - catch the 0.26.1-3 pattern on the old code;
  - pass on the fixed code;
  - keep an allow-list of known-safe uses, each with a one-line reason.
- **Azure setup:** `deploy/azure/setup.sh` uses GitHub's sign-in subject with ids, as the AWS setup does since commit 195cc61.
- **Refused sign-ins:** when the sign-in guard refuses an attempt, the app logs `SignInRefused`, with no address and no e-mail.
  The sign-in metric filter counts it with `SignInFailed`, so a sustained attack keeps the alarm up. A test pins the text and the
  filter, as 0.29.0 did for `SignInFailed`.
- **CloudFront error alarm:** an alarm in the edge stack (us-east-1) on the distribution's 5xx error rate, sending to the edge
  alert topic.
  - The workflow reads the distribution id from the app stack's outputs before deploying the edge stack.
  - On a first-ever deploy there is no distribution yet, so the alarm is skipped.
  - No `setup.sh` re-run is needed. If the deploy role lacks a permission this needs, the design is wrong; report it rather than
    widen the role.
- **0.29.0 left-overs:**
  - the DEPLOY_AWS heading "once, about 2 minutes", which now also creates cmms-dr;
  - the 00:00 UTC note, which should allow for a rollback's time;
  - the security check: `{}` as a secrets report is a problem, a missing gitleaks report after a clean Docker run is a problem,
    and the security job gets a `timeout-minutes`;
  - the spec's §1 table line about the workflow deploying cmms-dr.
- **0.14.0-1:** likely already closed by 0.29.0's headers. Prove it with a test that the logo download carries nosniff and the
  content policy.

## Left to the builder

- Where each fix lives and how it is structured, within the project's existing patterns.
- The exact message wording, in plain language, matching the existing messages, with Arabic.
- Splitting the work into tasks (about eight, grouped as above). Concurrency fixes use the project's existing patterns: row
  versions and unique indexes.
- Any item found already fixed: keep its test and say so in the task report.
