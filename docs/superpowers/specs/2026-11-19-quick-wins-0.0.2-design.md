# Quick wins for 0.0.2: design

*19 November 2026. Source: the DimoMaint comparison (Drive `1000 CMX/DimoMaint Improvements`), quick-win patches.*

## Intent

Eight small improvements that maintenance teams notice every day, learned from DimoMaint. They ship together as **one release, 0.0.2**, chosen by the user, with one commit per item so any item can be dropped before release.

## Goals

- **PM-2:** PM generation can skip assets that are down, avoid non-working days, and stop stacking work.
- **WO-4:** organizations can require labour, finished checklists and failure codes before a job is completed.
- **WO-5:** a printable job card for each work order.
- **WO-6:** a work order moves to In progress by itself when work starts.
- **WO-10:** duplicate a work order.
- **UX-2:** more work-order filters.
- **RD-2:** an alert bell in the header.
- **PM-4:** generate one upcoming PM occurrence now.

## Non-goals

These stay for later minors:
- per-schedule overrides of the PM rules
- meter reading captured on the work order
- automatic completion when every step is ticked
- custom statuses
- e-mail

**Anti-goal:** existing organizations (including the imported 4CSQL ones) must see no behaviour change until an admin switches a rule on.

## Constraints

- No database migration.
- Organization settings are stored as JSON (`TenantSettings`), so new settings default safely for existing tenants.
- One permission model: reuse the existing permission codes.
- English strings go in `web/src/locales/en.json`.

## Approaches

- **A. Organization-wide settings in `TenantSettings` (chosen).** No migration, one Settings page, small and quick.
- **B. Per-schedule and per-work-order fields.** More flexible, like DimoMaint, but needs EF migrations and more screens. Left for a later minor.
- **For the alert bell, two options:**
  - **Chosen:** one new `GET /api/alerts` endpoint that returns only the counts the user may see. One call, polled every 2 minutes.
  - **Rejected:** reuse three list/summary calls, which costs more calls and needs per-permission logic in the browser.

## Design

### PM-2 PM generation rules
New settings, all off by default:
- **`PmSkipAssetStatuses`** (asset statuses): skip a single-asset occurrence when the asset has one of these statuses. Round assets with these statuses drop out of the round, as Inactive and Disposed already do. The skipped occurrence still advances the schedule, and the preview and result say why ("Skipped: asset is Under repair").
- **`PmNonWorkingDays`** (weekdays): when a target date falls on one, the work order's planned start and due date move to the next working day. The schedule's cadence and duplicate key (`PmDueDate`) keep the original target date, so the dates don't drift.
- **`PmNoStacking`** (yes/no): a Scheduled-basis occurrence is skipped, and the schedule advances, while an earlier work order of the same schedule is still open, in progress or on hold. Actual-basis and meter schedules already behave this way.

### WO-4 Completion rules
New settings, off by default. They are checked when a work order moves to Completed, in the status endpoint, beside the existing "work done notes" rule:
- `RequireLaborToComplete`: at least one labour entry.
- `RequireAllTasksDone`: every checklist step ticked.
- `RequireFailureCodeForBreakdowns`: Breakdown work needs a failure code.

The errors come back as the usual field problems, so the completion dialog shows them.

### WO-5 Job card
- A print page at `work-orders/:id/print`, outside the app layout, like the PO print. A "Print job card" button on the work order opens it.
- The page shows:
  - the organization name, the WO number, title, status, priority and type, and the site, location and asset (number, name, serial)
  - the planned start and due date, assignees, requested-by, description, notes to technician, and the warranty notice
  - the checklist, grouped by asset on rounds, with tick, reading and remarks columns
  - labour and parts already booked, plus blank rows to fill in
  - lines for the completion notes (work done, cause, prevention, failure code, downtime) and signature lines (technician, supervisor or customer, date)

### WO-6 Automatic In progress
- New setting `AutoStartWork`, off by default.
- When it is on, logging labour or ticking a checklist step on an **Open** work order moves it to In progress. A status-history entry records "Started automatically: labour logged" or "…step done", and `StartedAt` is set.
- On hold and other statuses are left alone.

### WO-10 Duplicate
- A "Duplicate" action on the work order (needs `workorders.create`). It opens the new work-order form pre-filled from the original: title, description, type, priority, site, location, asset, trade, assignees, estimated hours and checklist steps (unticked).
- Dates, status, labour, costs, parts, completion details and the PM and request links are not copied.
- The action is hidden on PM round work orders, whose asset list the form can't set.

### UX-2 Work-order filters
- The API already filters by location (including sub-locations), asset (including its direct children) and assignee. The list gets pickers for these.
- New filters, in the API and on the screen:
  - created-between and due-between date ranges
  - a source filter: from PM, from a request, or raised directly
- Filters stay in the URL, as today.

### RD-2 Alert bell
- `GET /api/alerts` returns counts only for what the user may see:
  - overdue work orders, and how many are assigned to me (`workorders.view`)
  - requests waiting for triage (`requests.manage`)
  - parts at or below re-order level (`inventory.view`)
- A bell in the header shows the total. Its menu links each line to the filtered list.

### PM-4 Generate now
- On the forecast tab, the first upcoming occurrence of each schedule gets a "Generate now" action (needs `pm.generate`). The schedule form gets a "Generate next now" button.
- Both ask in a page dialog first, then call the existing `POST /pm/generate` with that schedule and date.

## Tests

- Server tests cover PM-2 (each rule), WO-4 (each rule), WO-6 (labour and step), the alerts endpoint (permissions and counts) and the new list filters (dates and source).
- The web app must type-check and build.
- The job card, duplicate, filters, bell and generate-now are checked in a running local stack.

## Release

- Add a `0.0.2` section to `CHANGELOG.md`.
- After review, the branch `feature/quick-wins-0.0.2` is merged into `main` only with the user's OK. Then `scripts/release.sh 0.0.2`, and the user pushes from GitHub Desktop.
