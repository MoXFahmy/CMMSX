# CMX 0.29.2 — Arabic and two-language polish (design)

Started 27 November 2026. The user asked to go ahead without design questions ("just dive in"), so every choice below that isn't
in the item list is Claude's call and is marked **(call)**. The item list is part 6 of `CMX left-overs up to 0.28.0.md` in the
CMX Drive folder. Each item keeps its tag (for example `0.6.0-2`) so it traces back to that file. The code survey is
`docs/superpowers/plans/2026-11-27-arabic-0.29.2-code-map.md`.

## Intent

CMX is used by Arabic-speaking teams. 0.6.0 added Arabic and right-to-left, and 0.28.0 let records carry an Arabic name. Since
then, Arabic readers still meet English words inside Arabic sentences, English values in exports and logs, charts and number
columns that don't mirror, and places that show or sort by the main name when an Arabic name exists. 0.29.2 closes those gaps
before 0.30.0, and makes it hard for new ones to slip in. It ends with a native Arabic review of all texts.

## Goals

- The 16 items and design limit 2 behave as described below. Each is proven by a test that fails on 0.29.1 and passes after.
- Two guard tests that fail the build on new gaps:
  - web: no new fixed left/right alignment or spacing;
  - server: no new user-facing English text without an Arabic entry.
- The deploy's tag step names the commit a tag points to, not the tag object.
- A review sheet of every Arabic text, with a first-pass list of suspect texts, ready for a native speaker.

## Non-goals

- New features, screens or settings. The only additions are messages, one window state (item 0.28.0-6), and the review sheet.
- Rewriting stored history. Old log rows and notes keep their stored English and are translated when shown.
- Translating text that is part of a record people edit (a work order's description, completion notes typed by a person).
- Isolating phone numbers and e-mail addresses as left-to-right runs inside Arabic text (not reported, larger change).

## Anti-goals (a failure even if the fix "works")

- English readers see any change other than the deploy message, the safety-note fallback (below) and the AI window's new state.
- A picked (Arabic) name fed back into an edit form and saved as the main name (the 0.28.0 rule).
- An export or import that worked in English stops working. Importers keep accepting English words.
- A chart, table or print page that mirrors in English.

## Constraints

- Tests first for every item, as in 0.29.1. If a test passes before any fix, the item is closed: keep the test, change no code.
- Server tests use `ApiFixture` and the Arabic-request helpers (code map §0). Web tests use Vitest.
- Every new text has English and Arabic. Server: `server/FourC.Cmms.Api/Localization/ar.json` (key = exact English, file sorted
  by key). Web: `web/src/locales/en.json` + `ar.json` (parity enforced by `locales.test.ts`).
- No database migration in this release.
- Arabic numbers keep Latin digits (`ar-EG-u-nu-latn`, the 0.6.0 choice); Arabic month names come from the `ar-EG` culture.
- Release with `scripts/release.sh 0.29.2`. The user pushes from GitHub Desktop and the pipeline deploys.

## Approaches

1. **One release in six tasks grouped by area, each reviewed, then a whole-branch review** (chosen). Same process as 0.29.0 and
   0.29.1. The groups barely share files, so each task can be judged on its own.
2. Fix only the 16 listed lines, without guard tests. Rejected: the survey shows the gaps keep coming back (two labels became ten),
   because nothing checks them.
3. Wait for the native review before building, then fix everything in one go. Rejected **(call)**: the code fixes don't depend on
   the review, and the review is easier on a release that already has the missing texts.

## Decisions (all Claude's calls, 27 November 2026)

| # | Item | Decision |
|---|---|---|

| 3 | 0.18.0-7, 0.17.0-10 | Add every user-visible server text that lacks Arabic, not only the two labels. A server guard test scans for message texts without an Arabic entry, with an allow-list for log lines, AI prompts and sample data (same shape as `GuardFilterLiftTests`). |
| 4 | 0.19.0-4, 0.20.0-2 | Dates inside sentences and report labels are formatted in the reader's language. This covers the five other reports' "As of" subtitles with the same fault. |

| 7 | 0.28.0-7 | Template steps carry no timestamp, so examples follow their template's last change (newest first). Editing only the steps must count as a change to the template. No migration. |
| 8 | 0.28.0-8 | Safety notes are never hidden: the reader's language when present, else the other language. Applies to the web work order page, the job card, e-mails and the phone. This is the one change English readers can see. |
| 9 | Design limit 2 | All list exports write fixed values (statuses, types, yes/no) in the app's language, not only the contract status. The web sends the app's language with the download, because a plain download link carries the browser's language. Importers keep accepting both languages. |
| 10 | 0.28.0-6 | The AI "fill in Arabic" window remembers, for as long as it is open, the texts the person unticked and the ones it couldn't draft, and doesn't ask for them again. A batch that drafts nothing offers Try again, Skip these and Close. Closing and reopening offers everything again. No new storage. |
| 11 | Review | The release does not wait for the native review. At the end Claude builds a review sheet and flags suspect texts. Corrections ship in a follow-up release. |

## Intended behaviour, item by item

- **0.6.0-1 Charts:** asset costs, measurements, home dashboard, reports and AI usage charts mirror in Arabic. Axis tick labels
  anchor correctly (the reports page's custom tick flips its text anchor).
- **0.6.0-2 Alignment:** 151 `ta="right"` become `ta="end"`, including 7 on print pages. 22 physical spacings become logical, 3
  borders become start-side borders. The location tree indents from the start side.
- **0.17.0-10:** "Person" has Arabic. New tests add a contact, address and rate to an existing contractor company, and a covered
  asset to an existing contract. If either fails, the save is fixed (the 0.12.1 child-row lesson).
- **0.18.0-7:** "Supplier's part number", "Pack" and the other labels and messages the guard finds have Arabic.
- **0.19.0-4:** the over-hours warning and "Planned after its due date" use Arabic month names in Arabic.
- **0.20.0-2:** the budget report's month rows and period subtitle are Arabic in Arabic, and so are other reports' "As of" lines.
- **0.21.0-12:** the list clash message shows the value as the reader sees it. The numbering failure says "work order" or
  "purchase order" in the reader's language.
- **0.25.0-5:** bulk-change summaries in the activity log and record history are Arabic for Arabic readers, old rows included.
- **0.28.0-1:** the PM compliance report, the PM calendar's "used by" and asset checklist template names show the reader's name.
- **0.28.0-2:** the work orders page's symptom, cause and remedy filters show the reader's names (values sent stay ids).
- **0.28.0-3:** the PM schedule list sorts by the shown name for Arabic readers.
- **0.28.0-4:** phone parts and templates can be found by their other-language name, offline too. The web location picker
  matches both names.
- **0.28.0-5:** switching language refetches every open list and page, so names change at once.
- **0.28.0-6:** as decision 10.
- **0.28.0-7:** as decision 7.
- **0.28.0-8:** as decision 8.
- **Design limit 2:** as decision 9. Sheet names follow the language too.
- **Deploy nit:** `scripts/tag-release.sh` reads the commit a tag points to. A re-run of a tagged commit says it's already
  tagged, without a false warning. `scripts/test-release.sh` checks the message.

## Left to the builder

- Exact Arabic wording for new entries, in the style of the existing file. The native review will polish it.
- The guard tests' exact scanning rules and allow-list format, within the shapes described in the code map.
- Which stored lines are translated when shown and which are only allow-listed, by decision 6's rule. Each one is reported.
- Splitting into tasks (about six, by area). Visual checks of mirrored charts, the planning grid and the location tree are done
  in the final review with screenshots where possible.
